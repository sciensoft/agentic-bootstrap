# Request

Cut 3 of the context-management improvements. Distinguish **reactive** rules (fire when a specific surface is touched — security, changes, UI, layered architecture, frontend) from **proactive-discipline** rules (apply on every relevant work unit when opted in — testing, metrics, telemetry). Reframe the `workflow-metrics.md` trigger row from reactive to proactive, add a proactive-discipline section to the rule body, extend the `Always` block's deferral bullet to name proactive-rule deferrals explicitly, and add a short intro paragraph in `Read before you act` naming the two flavors so future rules land in the right camp.

## Reasoning

The user's insight: the interview captures *intent*, not *usage*. When a project opts into metrics, the agent should instrument new features as part of building them — not wait for someone to ask "did you add metrics?". Section 6.3 of `AGENTIC-B.Improvements.md` (my "provisional rules" idea) was superseded by Cut 1's trigger-index math (unused rules cost one line, not the full body); dropping opted-in rules would create false-negative correctness debt when the project grows into the discipline.

The trigger index today mashes reactive and proactive rules together. Testing and telemetry are already worded proactively ("writing production code", "any new / changed code path"), so their rows already fire on every code change. Metrics is the outlier — its row fires only on "adding, changing or removing a metered event", which is reactive-only: new features never get instrumented because the trigger requires metering to already be there.

Deferrals are the other half: the user's *"no metrics for this turn"* is a legitimate override, but the discipline needs to survive it. Routing proactive-rule deferrals through `.docs/todos/` (with a revisit trigger like *"next commit that touches this subsystem"*) keeps the discipline honest without blocking short-term work.
