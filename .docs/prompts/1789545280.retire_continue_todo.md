# Request

Capture the Continue.dev retirement as a `.docs/todos/` entry rather than doing the removal work now. User's direction: leave Continue.dev support in place (it's harmless — existing users keep working, new files are inert without a Continue.dev install to consume them), but plant a retirement marker somewhere non-visible so the future work isn't lost. Explicitly not in `docs/index.html` — the landing page already reflects the discontinuation.

## Reasoning

Landing-page mention of Continue.dev implied active support for a discontinued product — fixed during the 2026-09-16 rebuild. The wider generator + docs sweep (Q2 answer space, Part 4 template, README/QUICKSTART/SECURITY, three example `best-practices.md` files) is real work — probably 20-30 minutes — and mixing it into the context-management merge would muddle what the merge is about. Meanwhile, existing users on Continue.dev keep working, and new users who pick it get an inert `.continue/config.json` that does no harm.

The `.docs/todos/` mechanism is exactly the "one file per deferred idea" pattern this project uses. Landing page stays clean of retirement announcements; the retirement plan lives with the other deferred work, indexed by `ls .docs/todos/`.

## Consulted rules

- `workflow.md` — new artifact-producing task; prompt file + commit + push.
- `workflow-todos.md` — this cut's whole output is a new todo entry; entry shape (title / Area / Refs / Context / Deferred because / Revisit when) followed exactly per §2 of the rule.
- `best-practices.md` (Markdown-content discipline) — heading hierarchy stable, cross-references use repo-relative paths from `.docs/todos/`.

Not applicable: `workflow-security.md`, `workflow-changes.md` (no user-visible surface changed — landing page untouched), `workflow-metrics.md` / `workflow-testing.md`.
