## Reasoning

The bootstrap *sells* the discipline of capturing deferred work as `.docs/todos/<kebab-slug>.md` entries with the Context / Deferred because / Revisit when shape. Tracking the maintenance rituals + community-phase plan *in the project itself* using *the same convention* is the dogfood test — and the user's framing ("follow what we sell") is correct: this is structurally important, not just symbolic.

Three files in this PR (not one) because the entries cover *three independent commitments* with *three independent triggers*:

1. **`quarterly-adapter-refresh.md`** — process commitment that recurs every 90 days. Lives until distributed maintainership replaces it.
2. **`doctor-mode-upstream-check.md`** — engineering commitment with three orthogonal triggers (user-reports-bug OR 50-stars-reached OR 2026-12-01-arrives). Different lifetime than the ritual.
3. **`community-phase-90-day-plan.md`** — months-long practice plan + the consistency-tracking convention. Different cadence (monthly retrospective) and different success criterion (6 consecutive months of consistent participation).

Bundling them into one file would conflate three different revisit triggers and three different "what does done look like" tests. The TODO format is per-idea for a reason.

The community-phase TODO is deliberately the longest of the three because it carries two payloads at once: the 90-day starter plan (the *work*) and the consistency-tracking convention (the *meta* — how the user will know whether they're keeping the practice). The git-log-as-audit-trail pattern leverages the same convention `workflow-todos.md` already establishes for the rest of the TODO directory.

### Why no CHANGELOG entry

The CHANGELOG covers notable changes to `AGENTIC-BOOTSTRAP.md` (the artifact users ship). These three TODOs are internal project-state about how the *maintainer* operates this repo — not changes to the file users consume. Per the workflow rules, no bump needed.

### Why no ADR

ADRs cover structural decisions about the project's shape. These are process commitments and a learning plan, not architecture changes. The pattern is already established by sibling TODOs like [`ai-engineer-summit-cfp.md`](./ai-engineer-summit-cfp.md), [`reach-tool-maintainer.md`](./reach-tool-maintainer.md), [`community-driven-adapter-contributions.md`](./community-driven-adapter-contributions.md) — community/maintenance commitments live as TODOs, not ADRs.

### Cross-links worth preserving

- `quarterly-adapter-refresh` ↔ `doctor-mode-upstream-check`: the manual ritual and its automated counterpart, each catching what the other misses.
- `quarterly-adapter-refresh` ↔ `community-driven-adapter-contributions`: the ritual is replaced (not supplemented) once distributed maintainership exists.
- `community-phase-90-day-plan` ↔ sibling community TODOs (`ai-engineer-summit-cfp`, `reach-tool-maintainer`, `agents-md-case-study-pr`, `demo-asset-90sec-recording`): the plan is the umbrella; siblings are specific actions inside it.
