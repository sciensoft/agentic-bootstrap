# Request

Real incident: a user was near the end of the 17-question interview when her VSCode session was taken over by a new project window; because the bootstrap only wrote `.agents/bootstrap.json` at the end of Step 5, every answer was lost. She had to restart the interview from Q1.

User's design directive: **single file, no `.agents/bootstrap.wip.json` companion.** The same `.agents/bootstrap.json` should capture in-progress state, done state, and the (done → in-progress → done) cycle when a re-run reopens a captured question. *"A simple status of done, or in-progress could capture both."*

## Reasoning

Rejected shape A (`.agents/bootstrap.wip.json` beside `.agents/bootstrap.json`) for the reasons the user named: two files means two synchronisation points, two `.gitignore` decisions, two paths for the agent to check. One file is honest.

Chosen shape: a top-level `interview_status` field on the existing `bootstrap.json` schema. Two values:

- **`"in_progress"`** — an interview is currently running (first-time or re-run). Answers dict has 0–17 populated keys; missing keys are what's left to ask.
- **`"done"`** — the interview is complete. Answers dict has all 17 keys (plus any keys added by newer bootstrap versions).

The transition `done → in_progress → done` is what happens when a re-run wants to re-ask a captured question (user's example: *"I answered Q12 Testing = No; I want to change that."*). Legacy `bootstrap.json` files written before this field existed have no `interview_status` key at all — the field-note handles that: **treat missing as `"done"`** because those files were only ever written on completion under the old protocol.

## Design decisions worth naming

- **Write on every answer, not batched.** A batched write (e.g. every 5 questions) would lose 1–4 answers on interruption. The per-question write is cheap (~1 KB JSON) and honest.

- **`interview_status` as a top-level field, not nested inside `answers`.** Keeps the answers dict a clean interview-answer surface. Status is metadata about the collection process; belongs at the same level as `bootstrap_version` and `last_run_at`.

- **No per-question status field.** An earlier draft considered `{"Q1": "answered", "Q2": "answered", "Q3": "next", ...}` — rejected because "which key is populated in the answers dict" already answers the same question with zero redundancy. First missing key = the next question to ask.

- **Legacy files (no `interview_status`) treated as `"done"`.** Any existing `.agents/bootstrap.json` was written under the old protocol, which only wrote on completion — so if it exists at all, the interview was complete. Safe assumption; documented in the field notes so a future contributor doesn't add a migration script for something that doesn't need one.

- **User-requested answer change temporarily flips to `"in_progress"`.** This handles the case the user explicitly named. Semantically clean: any time the agent is actively editing the answers dict, status is `"in_progress"`. Any settled state is `"done"`.

- **No `.gitignore` change.** `bootstrap.json` is already committed (Canon category); making the in-progress writes commit-visible is fine — a mid-interview commit would show an incomplete file, but that's an accurate reflection of the interview state and the user can decide whether to squash-merge or amend.

## Not touched (deliberately)

- **README / QUICKSTART / landing page** — the checkpoint is transparent to the user's mental model. They don't need to know the file schema changed; they just experience *"the interview resumed."* No visitor-facing surface needs updating.

- **`bootstrap_version` header bump** — no. This change goes into `[Unreleased]`; the lint's *"header matches most recent dated CHANGELOG entry"* invariant stays satisfied without a bump.

- **Doctor mode** — currently checks for stale `bootstrap.json` keys. Doesn't need updating to recognise `interview_status` explicitly; the missing-key check still works on the answers dict, and the field's presence is orthogonal to the doctor's drift-detection surface. If a future doctor-mode enhancement wants to report *"interview was interrupted at Q{N} and never resumed"*, that's a separate feature.
